#### Потоковая передача нескольких сообщений
При записи нескольких сообщений в один файл или поток, необходимо отслеживать, где заканчивается одно сообщение и начинается другое. Формат передачи данных Protocol Buffer не предусматривает самоограничения, поэтому анализаторы не могут самостоятельно определить, где заканчивается сообщение. Самый простой способ указать размер каждого сообщения перед его записью. При обратном чтении сообщения считывается размер, затем считываются байты в отдельный буфер, а затем выполняется синтаксический анализ буфера
>[!Warning]
>Для избежания копирования байтов в отдельный буфер, внимание на CodeInputStream, который можно настроить на ограничение чтения определенным количеством байтов

#### Большие наборы данных 
буферы протокола не предназначены для обработки больших сообщений.  Если размер сообщения превышает 1 мб, стоит рассмотреть другую стратегию
Буферы протокола подходят для обработки отдельных сообщений в *рамках* большого набора данных. Большие наборы данных состоят из множества небольших фрагментов, каждый из которых представляет собой структурированные данные. Не могут обрабатывать весь набор данных за один раз, но использование буферов протокола для кодирования каждого фрагмента значительно упрощает задачу. Работа ведется с набором байтовых строк, а не с набором структур.

#### Сообщения, описывающие себя
Буферы протокола не содержат описания собственных типов. Имея только необработанное сообщение без соответствующего .proto файла, определяющего его тип, сложно извлечь полезные данные

Содержимое файла .proto само по себе может быть представлено с помощью буферов протокола. Файл `src/google/protobuf/descriptor.proto` в пакете исходного кода определяет используемые типы сообщений. `protoc` может выводить `FileDescriptorSet`— представляющий собой набор файлов .proto— с помощью `--descriptor_set_out` опции. Таким образом, вы можете определить самоописывающееся протокольное сообщение следующим образом:

`syntax = "proto3"; import "google/protobuf/any.proto"; import "google/protobuf/descriptor.proto"; message SelfDescribingMessage {   // Set of FileDescriptorProtos which describe the type and its dependencies.  google.protobuf.FileDescriptorSet descriptor_set = 1;   // The message and its type, encoded as an Any message.  google.protobuf.Any message = 2; }`

Используя такие классы, как `DynamicMessage` (доступны на C++ и Java), вы можете написать инструменты, которые смогут манипулировать `SelfDescribingMessage`s.

Тем не менее эта функция не включена в библиотеку Protocol Buffer, потому что в Google она никогда не использовалась.

Этот метод требует поддержки динамических сообщений с использованием дескрипторов. Прежде чем использовать самоописывающиеся сообщения, убедитесь, что ваши платформы поддерживают эту функцию.

#### Разделение сообщений Protobuf
Сообщения Geode на основе Protobuf передаются в «разделенной» форме: размер сериализованного сообщения указывается в формате var-int, а затем следуют байты сериализованного сообщения. Это распространенная практика при использовании Protobuf для обмена данными, позволяющая узнать, сколько байтов нужно считать из сети при получении сообщения.

К сожалению, в Protobuf нет единой поддержки отправки и получения сообщений с разделителями. В некоторых языках для чтения сообщения ожидаемого размера можно использовать объект потока. В других языках необходимо прочитать часть сообщения в буфер, затем с помощью декодера выделить байты размера и продолжать чтение из сокета TCP/IP до тех пор, пока не будут прочитаны все ожидаемые байты. После этого можно декодировать сообщение Protobuf.

#### Вот варианты работы с сообщениями, разделёнными по размеру, на некоторых наиболее популярных языках, поддерживаемых Protobuf:
В C++ запись и чтение сообщений с разделением по размеру выполняются с помощью функций, описанных в google/protobuf/util/delimited_message_util.h.

#### ## Base 128 Varints
Целые числа переменной длины, или _варинты_, лежат в основе формата передачи данных. Они позволяют кодировать 64-битные целые числа без знака, используя от одного до десяти байтов, при этом для небольших значений требуется меньше байтов.

Каждый байт в varint имеет _битовый флаг продолжения_, который указывает, является ли следующий байт частью varint. Это _старший бит_ (MSB) байта (иногда его также называют _знаковым битом_). Нижние 7 бит являются полезной нагрузкой; результирующее целое число формируется путем объединения 7-битных полезных нагрузок составляющих его байтов.

Например, вот число 1, закодированное как `` `01` `` — это один байт, поэтому старший бит не установлен:

`0000 0001 ^ msb`

А вот 150, закодированное как `` `9601` `` — это немного сложнее:

`10010110 00000001 ^ msb    ^ msb`


#### Справочная документация по работе с классами буфера протокола C++
```
#include <google/protobuf/io/coded_stream.h>
namespace google::protobuf::io
```
Содержит классы:
- CodeInputStream
- CodeOutputStream
Оберки для ZeroCopyInputStream или ZeroCopyOutputStream сотвественно. Позволяют считывать или записывать отедльные фрагменты данных в различных форматах.
В частности реализуют кодирование varint для целых чисел, простое кодирование переменной длины, при котором меньшие числа занимают меньше байтов.

**Про кодирование:**
- биты 0-6: Семь битов кодируемого числа
- 7 бит:
  - 0, если это последний бит в колировке
  - 1, если за ним следуют другие байты
- Первый байт содержит младшие 7 бит числа, второй байт (если присутствует) содержит следущие наименее значимые 7 бит и тд

#### Классы
1. CodeInputStream
Класс, который читает и декодирует двоичные данные, состоящие из целых чисел в кодировке varint и кусочков фиксированной ширины.
```
#include <google/protobuf/io/coded_stream.h>
namespace google::protobuf::io
```
Большинство методов CodedInputStream, возвращающих логическое значение, возвращают false, если возникает основная ошибка ввода-вывода или если данные неправильно сформированы. Как только происходит такой сбой, CodedInputStream прерывается и больше не используется. После сбоя вызывающие также должны предположить, что могли произойти arg записи в "out", хотя из этих записей нельзя определить ничего полезного.
**Члены:**
- explicit	
CodedInputStream(ZeroCopyInputStream * input) - Создайте CodedInputStream, который считывает данные из заданного ZeroCopyInputStream.
- bool Skip(int count) Пропускает несколько байтов.
- bool CodedInputStream::ReadVarint32(uint32 * value) - Чтение целого числа без знака с кодировкой Varint, усечение до 32 бит.
- Limit CodedInputStream::PushLimit(int byte_limit)
Устанавливает ограничение на количество байтов, которые может быть прочитан потоком, начиная с текущей позиции.
Как только поток достигнет этого предела, он будет действовать так, как будто был достигнут конец входных данных, пока не будет вызван PopLimit().
Как следует из названий, поток концептуально имеет стек ограничений. Всегда применяется самый короткий лимит стека, даже если он не является верхним.
Значение, возвращаемое PushLimit(), является непрозрачным для вызывающего и должно быть передано без изменений в соответствующий вызов PopLimit()
Чтение 32-битного значения эквивалентно чтению 64-битного значения и приведению его к uint32, но может быть более эффективным.
- void CodedInputStream::PopLimit(Limit limit)
Вырывает последнее ограничение, введенное PushLimit().
Входные данные должны быть значением, возвращенным этим вызовом PushLimit()
